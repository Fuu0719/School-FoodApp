## 一、人工智慧與推薦系統

### 1. 你們的人工智慧應用在哪裡？

建議回答：

> 本專題的人工智慧應用在餐點候選篩選、加權評分與推薦排序，採用可解釋的規則式推薦系統，不是生成式 AI 或深度學習。系統先依使用者的飲食偏好、忌口、預算、距離、庫存及營業狀態排除不合適的餐點，再依偏好、距離、預算、減廢價值及使用者直接回饋計算推薦總分。最後依分數排序，並在畫面顯示各項分數與推薦原因，讓使用者知道餐點為什麼被推薦。

技術定位：

- 中文：可解釋的規則式推薦系統。
- 英文：Explainable Rule-based Recommendation System。
- 結合內容式推薦與多條件加權決策。
- 不是生成式 AI、神經網路、深度學習或經資料訓練的預測模型。

### 2. 規則式系統也算人工智慧嗎？

建議回答：

> 算。人工智慧除了機器學習，也包含專家系統、知識表示、規則推理及搜尋決策等方法。本專題將餐飲選擇條件轉換成系統可執行的排除規則與評分規則，再由系統自動完成候選篩選、分數計算及排序，因此屬於規則式人工智慧。不過我們會明確說明目前沒有進行機器學習模型訓練。

### 3. 專題實際如何進行推薦？

推薦分為三個階段：

1. 候選篩選：排除超出預算、超出距離、不符合偏好、含有忌口食材、無庫存、已過期或目前無法供應的餐點。
2. 加權評分：計算偏好、距離、預算、減廢價值及使用者回饋分數。
3. 排序與解釋：依總分由高至低排列，並顯示推薦總分、各項分數及推薦原因。

目前評分權重：

| 評分項目 | 權重 | 說明 |
| --- | ---: | --- |
| 偏好符合度 | 35% | 餐點標籤與會員偏好的符合程度 |
| 距離符合度 | 18% | 距離越接近可接受範圍，分數越高 |
| 預算符合度 | 18% | 價格越接近預算區間中心，分數越高 |
| 減廢價值 | 19% | 即期餐點具有較高減廢優先分數 |
| 使用者回饋 | 10% | 星級及「會再回購」、「不符合偏好」等標籤 |

概念公式：

```text
推薦總分
= 偏好符合度 x 0.35
+ 距離符合度 x 0.18
+ 預算符合度 x 0.18
+ 減廢價值 x 0.19
+ 使用者回饋 x 0.10
```

### 4. 為什麼不用機器學習？

建議回答：

> 目前專題的真實使用者與互動資料量不足，直接使用協同過濾或深度學習容易遇到冷啟動、資料稀疏及結果難以驗證等問題。規則式推薦不需要大量訓練資料，推薦依據透明，也較符合目前專題規模及食品推薦需要清楚說明原因的需求。取得足夠且經使用者同意的資料後，才適合研究學習排序或協同過濾。

### 5. 系統會自主學習嗎？

建議回答：

> 目前不會自主訓練，也不會自動修改推薦權重。使用者送出的星級及回饋標籤會直接參與後續評分，但收藏、瀏覽與購買紀錄目前不會自動訓練模型。因此系統可稱為回饋感知的規則式推薦，不能宣稱具備機器學習或自主學習能力。

### 6. 推薦權重是怎麼決定的？

建議回答：

> 權重依專題目標與功能優先順序人工設定。個人偏好是推薦的主要目的，因此占 35%；距離與預算各占 18%；減廢是專題核心，因此占 19%；直接回饋占 10%。目前權重屬於設計參數，尚未由大量使用者資料訓練取得。未來可透過使用者實驗、問卷或離線評估調整。

不可回答「AI 自己算出權重」。

### 7. 推薦系統的可解釋性在哪裡？

建議回答：

> 每一項推薦分數都可拆解成偏好、距離、預算、減廢及回饋五個部分，App 會顯示各項分數與推薦理由。開發者及使用者都能追溯餐點得分原因，因此屬於內生式可解釋性，不需要在黑箱模型完成預測後，再以 SHAP 或 LIME 等工具推測原因。

### 8. 這和一般篩選功能有什麼不同？

建議回答：

> 一般篩選只判斷符合或不符合。本系統先篩選，再對通過條件的餐點計算多項分數並排序。因此餐點即使都符合基本條件，仍會因偏好、價格、距離、減廢程度及回饋不同而有不同排名。

### 9. 如何證明推薦準確？

建議回答：

> 目前已透過自動化測試驗證篩選規則、分數範圍、排序結果及回饋是否正確影響分數，但尚未完成大量使用者的推薦準確率研究。因此我們能證明系統依設計規則正確運作，不能宣稱已證明具有高預測準確率。未來可使用 Precision、Recall、NDCG、點擊率、採納率或使用者滿意度評估推薦成效。

### 10. 為什麼稱為內容式推薦？

建議回答：

> 系統主要比較餐點本身的標籤、價格、距離、即期狀態等內容特徵，與會員主動設定的偏好及限制，再計算符合程度，所以屬於內容式推薦。系統目前沒有根據其他使用者的相似行為進行推薦，因此不屬於協同過濾。

### 11. 有使用協同過濾或混合式推薦嗎？

建議回答：

> 沒有。協同過濾與混合式推薦只在文獻探討中作為相關方法介紹。目前實作是規則式內容推薦與多條件加權評分，沒有比較不同使用者之間的相似度，也沒有訓練協同過濾模型。

### 12. 減廢如何影響推薦？

建議回答：

> 餐點資料包含即期狀態與減廢優先分數。會員啟用減廢偏好時，即期餐點會獲得減廢項目的分數，但仍須先通過預算、距離、偏好、忌口、庫存、期限及營業狀態等條件。系統不會為了減廢而推薦已過期或不符合基本需求的餐點。

### 13. 目前系統使用哪些回饋？

建議回答：

> 目前直接參與推薦的是保存在裝置端的餐點星級與回饋標籤。「會再回購」會提高回饋分數，「不符合偏好」會降低回饋分數。收藏、瀏覽與購買紀錄可同步會員帳號，但搜尋紀錄與推薦回饋尚未雲端同步，也不會自動轉換成模型權重。

### 14. 推薦運算是在前端還是後端？

建議回答：

> 商品、會員偏好及活動資料由後端 API 與 MySQL 提供，目前推薦分數與排序主要在 Flutter App 端執行。後端 `/api/recommendations` 尚未完成，因此不能宣稱完整的雲端 AI 推薦引擎已上線。

## 二、答辯用語界線

### 可以使用

- 可解釋的規則式人工智慧。
- 可解釋的規則式推薦系統。
- 內容式推薦。
- 多條件加權評分。
- 回饋感知的推薦。
- 已驗證推薦規則與排序正確運作。
- 機器學習與協同過濾是未來擴充方向。

### 不可過度宣稱

- AI 會自主學習所有使用習慣。
- 已使用協同過濾或混合式推薦。
- 已使用深度學習、神經網路或生成式 AI。
- AI 自動算出最佳權重。
- 已證明推薦具有很高準確率。
- 瀏覽、收藏及購買會自動改變偏好權重。
- 已串接便利商店官方即時庫存。
- 完整雲端 AI 推薦引擎已完成。

## 三、網站與管理後台問答

### 15. 為什麼已經有 App，還要做網站？

> 網站負責專題介紹、功能說明、法律文件與 Android APK 下載，降低安裝及了解專題的門檻；管理員也需要不依賴手機的營運查詢介面。會員與商家的完整日常操作仍以 App 為主，網站沒有取代 App。

### 16. 網站使用什麼架構？

> 網站採原生 HTML、CSS、JavaScript，由既有 Node.js／Express 服務直接提供，因此不需要另一套前端伺服器。網站與 App 共用 REST API 和 MySQL，但瀏覽器不能直接連資料庫。

### 17. 網站目前有哪些功能？

> 公開部分包含專題首頁、核心功能、使用流程、APK 下載、隱私權政策與服務條款。受保護的管理後台可查看日、週、月摘要，以及會員、商家、餐點、訂單清單、搜尋、日期篩選、分頁及 CSV 匯出，也可暫停或恢復商家。

### 18. 網站是否也能讓會員和商家操作？

> 目前正式公開網站沒有開放會員與商家工作台，完整流程仍在 Flutter App。版本庫保留部分早期網頁原型，但現行路由會把舊購物車及整合頁轉回專題首頁，所以答辯時不能把原型當成已發布功能。

### 19. 管理後台如何保護？

> 管理員密碼只保存 scrypt 雜湊。登入有限流，成功後使用兩小時有效的隨機 session，透過 HttpOnly、Secure、SameSite=Strict Cookie 傳送。管理 API 會逐次驗證 session，頁面不可快取，CSV 也會處理試算表公式注入。

### 20. 網站和 API 為什麼使用同一服務？

> 專題規模以單一部署單元較容易維護，網站可直接同源呼叫管理 API，也能共用 Cloudflare HTTPS、安全標頭與 Windows 服務。但管理 session 目前在單一 Node 程序記憶體，未來若要多台後端，需改成共享 session 儲存。

### 21. migration 011 解決什麼問題？

> 它加入付款到期與庫存釋放時間，讓未付款訂單逾期後能取消並只恢復一次庫存；也記錄會員與商家切換 session 的來源，使登出及撤銷能精準處理。套用時會清除無來源資訊的舊 session，因此使用者需重新登入。

### 22. 最新測試結果是什麼？

> 2026-10-27 本機 `flutter analyze` 為 0 issues，Flutter 128 項通過、2 項跳過；Node 77 項通過、4 項需要真實 MySQL 的整合測試跳過。正式部署仍要在學校端執行 `test:mysql`，不能把本機略過項目算成通過。
